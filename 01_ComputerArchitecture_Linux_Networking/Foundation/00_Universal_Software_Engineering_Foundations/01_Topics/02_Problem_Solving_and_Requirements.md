# Problem solving, computational thinking and requirements

> **Priority:** Core · **Study window:** 1–2, then every week · **Approximate focused time:** 12–15 (overlaps with weekly plan)

## Why it is universal

Problem formulation, abstraction and testable requirements transfer to every software domain.

## Detailed table of contents / concepts to cover

- [ ] Problem statements, actors, scope and non-goals
- [ ] Inputs, outputs, preconditions and postconditions
- [ ] Decomposition into small, verifiable functions
- [ ] Pseudocode, flowcharts and decision tables
- [ ] Invariants, boundary cases, failure paths and assumptions
- [ ] Functional vs. nonfunctional requirements: performance, security, accessibility, reliability
- [ ] Acceptance criteria and traceability from requirement to test

## How to learn it

1. Rewrite vague requests as explicit examples and counterexamples.
2. Draw a flow or pseudocode before opening the editor.
3. Create 3 normal, 3 boundary and 3 failure cases per medium task.
4. Review your specification with AI, then challenge suggested assumptions.

## Required exercise

Specify a resource-booking or inventory-allocation program, including duplicate requests, invalid IDs, conflicting reservations and expected error messages.

## Independent exit criteria

- [ ] Can decompose an ambiguous feature into small tasks.
- [ ] Can write acceptance criteria another person could test.
- [ ] Can distinguish scope changes from implementation changes.

## AI collaboration exercise

Ask an AI assistant for an alternative approach, at least three failure scenarios and a code/design review. Validate the suggestions independently, make one targeted improvement and describe what you accepted or rejected and why. Never treat the AI answer itself as evidence of correctness.
